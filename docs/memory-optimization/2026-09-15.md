# Kubernetes memory optimization report — 2026-09-15

## Scope and method

- Context: `context-cfc3fpsrexa` (OCI Wafflestudio cluster)
- Namespaces: all
- Snapshot: Metrics Server container working-set memory
- History: Prometheus `node_namespace_pod_container:container_memory_working_set_bytes`
- Window: 7 days, sampled hourly for right-sizing candidates
- 30-day analysis is not possible yet: Prometheus retention is `10d`
- Requests and limits came from the live Pod specs; ReplicaSet and Job owners were
  resolved to Deployment and CronJob.

The non-`kube-system` snapshot total was 15,419Mi working set against 17,444Mi
of memory requests. A low total gap does not mean requests are accurate: several
small services over-reserve heavily while JVM, MongoDB, and Prometheus workloads
run above their requests.

## Code-level findings by team

### Platform / `waffle-k8s-admin`

- Prometheus has 126,150 active head series and was at 94% of its memory limit.
  The custom `envoy-stats` job contributes 16,221 series. The unused
  `istio_request_bytes_bucket` and `istio_response_bytes_bucket` metrics
  account for 9,280 series (7.36% of the head). The patch drops only these two
  byte-distribution histograms and retains request counters and latency buckets.
- Istiod stayed between 83Mi and 92Mi for seven days. A 256Mi request is 2.8x
  the observed maximum and a 512Mi limit is 5.5x.
- Argo CD application-controller and Prometheus are not memory-reduction
  candidates. Grafana also has no request/limit despite a 7-day maximum near
  705Mi; resource policy should be added in a separate reliability PR.
- Loki stayed below 124Mi; a 192Mi request gives 1.55x headroom.

### Pupuri — repository `wafflestudio/pupuri-bot`, CODEOWNER `@woohm402`

- `GET /dashboard` called `find().toArray()` for the entire MongoDB `logs`
  collection, retained every full document, reduced it twice with linear
  searches, then serialized the graph again into HTML.
- Every request also constructed new Slack and Truffle clients.
- [pupuri-bot#125](https://github.com/wafflestudio/pupuri-bot/pull/125) moves the graph reduction into a MongoDB `$facet`
  aggregation and reuses clients. Result memory is bounded by the number of
  users and edges rather than the number of historical log documents.
- Until that image is deployed, the 128Mi limit is raised to 256Mi. The request
  remains 128Mi, so this safety change does not reserve more node memory.

### Siksha — repository `wafflestudio/siksha-spring`, GitHub team `siksha`

- The image sets both `InitialRAMPercentage` and `MaxRAMPercentage` to 60.
  In production this produced a 616Mi initial/max heap, while the live heap had
  about 274Mi used plus 153Mi metaspace. The 7-day peak reached the 1Gi limit.
- [siksha-spring#158](https://github.com/wafflestudio/siksha-spring/pull/158) changes only initial heap from 60% to 25%; max heap remains 60%.
  This can reduce committed startup heap by about 360Mi in prod and 269Mi in
  dev without reducing peak heap capacity.
- The GitOps override makes the fix effective before the next application image.

### SNUTT — repositories `snutt` and `snutt-ev`,
CODEOWNERS `@wafflestudio/snutt-server @PFCJeong`

- MongoDB is not safe to reduce: prod reached 912Mi of a 1Gi limit and dev has
  three historical OOM kills.
- The lecture-sync CronJob repeatedly reached roughly 1.28–1.31Gi; its 2Gi limit
  is justified. Dev's 256Mi request is below its observed peak and should be
  corrected separately.
- Prod replicas are balanced: `snutt-ev` was 139–180Mi (1.29x) and
  `snutt-ev-web` was 317–337Mi (1.06x).
- Theme-market stayed below 82Mi, so dev/prod requests are reduced to 128Mi.
  The missing memory limits on theme-market and ev-web remain a reliability gap.

### Hangsha — repository `wafflestudio/hangsha-server`

- The Python Kiwi service constructs a global `Kiwi()` model at import time.
  Its process RSS was about 486Mi against a 512Mi limit. This is a static model
  footprint, not a leak; lowering memory is unsafe.
- The Java API had a 128Mi max heap, about 68Mi used old generation, 104Mi used
  metaspace, and about 433Mi process RSS. No unbounded application cache was
  found. Native Memory Tracking is required before changing its limit.
- Only Valkey requests are reduced.
- No repository team or CODEOWNERS entry was visible to the auditing account.

### Waffle Alert — repository `wafflestudio/waffle-alert`,
team `waffle-k8s-admin`

- The Java child process used about 481Mi RSS at a 512Mi limit.
- The Kubernetes watcher processes the response line-by-line and uses three
  bounded threads; no accumulating informer cache was found.
- The large baseline is consistent with Spring Boot 4 + JPA/Flyway + OCI SDK +
  resilience dependencies. The JRE image lacks `jcmd`, so a staging image with
  `-XX:NativeMemoryTracking=summary` is needed before a safe reduction.

### SnuClear — repository `wafflestudio/snuclear-server`

- The service used 624Mi and reached about 625Mi over seven days at a 768Mi
  limit. No obvious unbounded cache was found, and its JRE image has no

- No repository team or CODEOWNERS entry was visible to the auditing account.

## Rollout and verification

1. Merge the source changes for Pupuri and Siksha first.
2. Sync dev namespaces and platform changes during a staffed window.
3. For 24 hours, alert on OOM/restarts and on working set above 80% of limit.
4. Sync production request changes.
5. Observe for seven days. Compare p95/max, node allocatable requests, pending
   Pods, and autoscaler scale-down behavior.
6. Roll back the affected manifest if working set exceeds the new request for
   sustained periods during node pressure, or if restart/OOM count increases.

Prometheus stops ingesting the 9,280 matching series from the next successful
scrape. They do not disappear from every Prometheus count immediately: stale
head series age out, and historical samples expire under the current 10-day
retention. If Istio byte-distribution dashboards are later required, revert only
the metric relabel rule.
