# DB 백업 현황 조사 및 정책 제안 — 2026-11-04

DB 백업 현황 조사 결과와 제안이다. 문서만 추가하며 클러스터·OCI 설정은 바꾸지 않는다.

## 조사 방법

- `kubectl get statefulset,pvc,pv -A`로 클러스터 내 DB와 볼륨을 확인
- PV의 `volumeHandle`(Block Volume OCID)마다 OCI CLI로 조회
  - `oci bv volume-backup-policy-assignment get-volume-backup-policy-asset-assignment`
  - `oci bv backup list`
- 실제 사용량은 Prometheus `kubelet_volume_stats_used_bytes`
- `oci mysql db-system get`, `oci mysql backup list`로 공용 MySQL 확인
- 레포 전체에서 backup / mongodump / pg_dump / snapshot / velero 관련 매니페스트 검색 → 없음
- AWS RDS는 권한이 없어 확인하지 못함

- shape `MySQL.Free`(Always Free), 50GB, 단일 인스턴스(HA 아님), 2026-02-12 생성

| 항목 | 현재 값 | 의미 |
|---|---|---|
| 자동 백업 | 켜짐, 매일 09:39 UTC(18:39 KST) | |
| **보관 기간** | **1일** | 항상 최신 백업 1개만 남음 |
| **PITR** | **꺼짐** | 백업 사이 시점으로 되돌릴 수 없음 |
| 다른 리전 복사 | 없음 | |
| 삭제 보호 | 켜짐 | 인스턴스 실수 삭제는 막힘 |

즉 12개 스키마 모두 **최근 18:39 시점 한 개로만** 되돌릴 수 있다. 문제를 다음 백업(18:39) 전에 발견하지 못하면 문제 이전 상태로 복구할 수 없다.

Always Free DB system은 백업 계획이 고정이다: 1일 보관, PITR·수동 백업·다른 리전 복사·보관 기간 변경 불가 ([문서](https://docs.oracle.com/en-us/iaas/mysql-database/doc/creating-always-free-db-system.html)). 백업을 Object Storage로 내보내는 `oci mysql backup export`도 시험했으나 `does not allow 'ExportBackup' operation, because it is a backup of an Always Free DB system`(409)으로 거부됐다. 또 Always Free DB system은 테넌시당 1개라, 백업 복원(=새 DB system 생성)은 유료 DB system으로 해야 한다.

## 제안

### 1. 볼륨 백업 정책 일괄 적용

| 범위 | 추가 볼륨 | 추가 비용(월) |
|---|---|---|
| **prod DB만 (slack-viz, n8n) — 권장** | 2개 | 약 $1~1.5 |
| + allclear-dev | 3개 | 약 $1.5~2 |
| 사용 중인 PVC 전부 (prometheus, loki 포함) | 약 7개 | 약 $4~5 |
| 미사용 snutt-dev 볼륨 bronze 해제 | -1개 | 약 -$0.25 |

prometheus(보존 10일)·loki(보존 14일)는 짧게 보관하는 데이터라 백업 실익이 거의 없고, hangsha-manticore는 재색인으로 복구된다.

```sh
oci bv volume-backup-policy-assignment create --asset-id <volume OCID> --policy-id <gold policy OCID>
```

- 서비스 중단 없음, 할당 삭제로 되돌릴 수 있음
- 비용은 위 표 기준 (prod DB 2개 월 약 $1~1.5)
- 다음 날 `oci bv backup list`로 첫 백업 생성 확인 후 이 문서 현황표 갱신

### 2. 공용 MySQL 백업 방식 결정

| 안 | 방법 | 효과 | 비용·부담 |
|---|---|---|---|
| **A (권장)** | Always Free 유지 + 매일 새벽 `mysqldump --single-transaction` CronJob → 백업 전용 버킷, lifecycle로 N일 뒤 삭제 | 7~14일 전 시점으로 복구, 스키마 단위 복구 가능, 새 DB system 불필요 | 덤프 하루 약 1.5GB(8월 전체 덤프 1.39GB 기준) → 7일 약 10GB, **월 $0.1 안팎**. 새벽에 1 ECPU 인스턴스 부하 |
| B | 유료 shape으로 전환 | 보관 최대 35일, PITR | MySQL.2(2 ECPU, 16GB) 기준 **월 약 $56** (ECPU $0.0366×2×730h ≈ $53.4 + 스토리지 50GB×$0.04 = $2 + 백업 약 $1). 새 DB system 이전·서비스 7개 접속 주소 변경 |
| C | 현 상태 유지 | — | 위험을 인지하고 보류 |

- A를 택하면 첫 덤프 후 dev 스키마에 한 번 복원해 덤프가 유효한지 확인

### 3. 안 쓰는 볼륨 정리

- 위 "정리 후보 볼륨" 5개를 각 팀(snutt, hangsha) 확인 후 삭제

### 하지 않는 것

- 백업 감시 CronJob, 정책 자동 할당: PVC 재생성은 드물고 계획된 작업이라 보류. 대신 아래 주의 사항으로 대체
- 스냅샷 복구 리허설: OCI 표준 기능이라 보류
- hangsha-manticore 백업: 재색인으로 복구 가능

### 주의 사항

> PVC를 새로 만드는 작업(StatefulSet·볼륨 이름 변경, 네임스페이스 재생성, StorageClass 변경 등)을 하면 새 볼륨에 백업 정책을 다시 할당할 것.
